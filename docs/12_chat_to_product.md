# 12 只靠聊天做出成品：模式、初衷卡、選擇頁

服務 `PURPOSE.md` 初衷 8。不列入每輪必讀：建置時讀一次，談需求、開選擇題、寫工單時再讀。

## 規則

### 一、先選模式

1. 使用者貼完啟動提示詞，總監的**第一則回覆只問一題**：一般模式還是小白模式。各附一句說明：
   - **一般模式**：會看到 plugin、工作線、設定這類技術問題，由你決定。
   - **小白模式**：你只要說想做什麼、看起來對不對；技術的事總監照預設決定，做完告訴你。
   啟動提示詞已經寫明模式，就不再問。
   選了小白模式，**同一輪**就開始談需求：只做唯讀確認、在 repo 外寫最少狀態，問第一個需求問題；完整建置延到談完需求、開第一位 worker 前（`BOOTSTRAP`「小白快速路徑」）。一般模式維持原順序。
2. 記錄：第 3 步建好 `DIRECTOR/` 後，寫進 `director_work.json` 的 `"mode": "general"` 或 `"beginner"`，和 `DIRECTOR_OPERATING_RULES.md` 開頭；在 `DECISION_REGISTER.md` 登記成 PO 指示。使用者之後隨時能換模式，換了照樣登記。
3. 兩種模式的安全底線一樣：推送、公開、付費、刪除、帳號、影響其他專案的設定，都要使用者同意（`docs/08`）。小白模式只是把問法換成白話，例如「要把成品放到網路上讓別人看嗎？」，不是跳過。

### 二、小白模式改了哪些步驟

| BOOTSTRAP 步驟 | 一般模式 | 小白模式 |
|---|---|---|
| 3、4、7、8、10 建置 | 照順序做完才談需求 | 快速路徑：談完需求、開第一位 worker 前才做（壓縮門檻只設定那位 worker 的資料夾） |
| 6 待決頁 | `PO_PENDING.md` 加聊天；選擇頁先問，同意且可用才用 | 同左，問法用白話（「需要我把選擇題和圖片放在你自己的 Claude 頁面，讓你點選嗎？直接在這裡回答也可以。」）；沒同意或用不了，在聊天問、總監存進 `PO_PENDING.md`（`docs/11`「選擇頁的授權與備援」） |
| 7.7 `hook_guard.py` | 問要不要裝 | 不問、不裝 |
| 9 無關 plugin | 列清單問 | 不問；`plugins_off` 留空，什麼都不關 |
| 12 工作線編制 | 草案問 PO | 總監照 `docs/05` 定第一批（通常一條 worker 線），登記 DD，寫進初衷卡「由總監決定的事」；開線的同意併進「卡片對，請開助手」那一句，不另外問 |
| 13 第一份回報 | 六點，含技術數字 | 三句白話：準備好了、接下來要聊需求、有什麼要你點頭的；技術細節只寫在檔案；快速路徑下併進那一則 |
| 每次問問題 | 可以問技術問題 | 只問「要做什麼、像什麼、好不好、可不可以」；問不出白話的，總監自己決定並登記 DD |

### 三、談需求，寫專案初衷卡

1. 開工前一定先有 `DIRECTOR/BRIEF.md`（`templates/BRIEF.md`），兩種模式都一樣。已有 `LOCKED` 的卡就跳過這一節。
2. 一次問一到三題，用使用者的話，從大到小：做給誰、要做出什麼、一定要有的、絕對不要的、做完長怎樣。小白快速路徑的第一題固定是「這是給誰用的？第一版讓他做成哪一件事就有用？」。使用者說不清楚時，給兩三個具體例子讓他挑，不要用術語追問。
3. 談到表裡每一列都填得出來，就把整張卡用白話貼給使用者看，問「這樣對嗎？」。使用者說對，才把狀態改成 `LOCKED`、記下時間（讀系統時鐘）、在 `DECISION_REGISTER.md` 登記。沒說對之前不派任何工單。要同時問開工，照下面第 6 點。
4. **鎖定後只有使用者能改。** 總監發現需要改（做不到、互相矛盾、使用者後來說的話跟卡不一樣），在選擇頁開一題問，不自己改。改了版次 +1，再請使用者確認一次。
5. 有選擇頁時，把卡的摘要同步寫進 db 的 `brief/current`，讓使用者隨時看得到。
6. **一句回覆同時確認卡和授權開工**（兩種模式都適用）。把卡和開工說明放在同一則貼出，說清楚：第一批做到哪裡就交給你看、開幾位 AI 助手、用現有的 Claude 額度與額外費用（沒有就寫 0 元；時間只是估計就標「估計」；讀不到用量就說不知道）、會新增或修改哪些檔案和在哪份工作副本、公開、上傳專案內容、付費要另外問。貼出前先備好首批工單、跑完 `gate_check --order` 和追溯核對；Strict 的規格審查要在貼出前做完（`docs/11`）。同一筆待決項（`templates/PO_PENDING.md`）記下卡的版次、首批工單的版次與雜湊、工作線與範圍。範本（以店員班表為例）：

   > 我把第一版整理成這張卡。它是給店員上班前看的。打開後按一下「今天」，就能看到今天的範例班表。用測試資料，先做到這個流程能用。顏色等你看到畫面再選。
   >
   > 如果你同意，我會請一位 AI 助手做這一批，再做一次獨立檢查。會用你現有的 Claude 額度，額外費用是 0 元。約 20 分鐘是估計，做到可以查看第一版就先交給你。
   >
   > 我會在專案的本機工作副本新增 `index.html`，並加上這份副本的本機設定 `.claude/settings.local.json`；Git 的本機忽略清單會加一列，讓設定檔留在本機。工單和檢查紀錄放在專案旁的 `DIRECTOR/`。公開、上傳專案內容或付費各自需要另外同意。
   >
   > 如果卡片對，而且你要我現在開工，回「**卡片對，請開一位 AI 助手做這一批**」就可以。想先改內容，直接說哪裡要改。

   使用者的回覆照下表判讀，兩個決定仍分別登記在 `DECISION_REGISTER.md`：

   | 使用者回覆 | 狀態 | 總監做什麼 |
   |---|---|---|
   | 只說卡對（沒說要開工） | `LOCK_ONLY` | 鎖卡；開工之後另問 |
   | 卡還是草稿，只說「開工」 | `NO_START` | 不開線；回「卡還沒確認，這樣對嗎？」 |
   | 明確說卡對、而且要開一位助手 | `LOCK_AND_USER_ASKED` | 依序：記錄同意並鎖卡 → 核對範圍和工單雜湊跟貼出的一致 → 做完開線前準備（壓縮設定，`BOOTSTRAP` 第 7 步）→ 寫 `DISPATCH` → 同一輪 `start_session` |
   | 只回「收到」「好」，沒指明 | `NO_START` | 當作還沒答，換一句白話再問一次 |
   | worker、計時器或 Artifact 喚醒的那一輪 | `NO_START` | 只能留提案卡（`docs/11`） |
   | 核准後範圍或工單雜湊變了 | `NO_START` | 重新貼出說明，再問一次 |
   | Strict 規格審查沒做完 | `NO_START` | 先審完再貼 |

7. **卡可以只鎖第一階段**。`templates/BRIEF.md` 有選填的「第一階段」：B 表只填這一階段已確認的使用者、核心動作、限制和可觀察的驗收；一開始就會影響能不能用的要求（無障礙、品牌）照常列 B。配色、字型、版面這類看過才知道的事，放在卡上的「待預覽」，**不編 B 號**：`trace_report.py` 把表格每列第一欄的編號都當待做需求，編成 B-6 會一直列在「沒有工單的需求」。第一個預覽先走成品檢查（`docs/07`），讓使用者實際完成核心動作；有了真實畫面（至少兩種）才開選擇題，連回既有的 B 號。選擇若會改到已鎖的 B 項，照第 4 點重開確認、版次 +1。
8. **追溯指令**：派工前、每個 gate 前，卡和決策登記表一起查：

   ```text
   python -I -X utf8 <WS>/DIRECTOR/tools/trace_report.py --orders <WS>/DIRECTOR/orders --reports <報告資料夾> --decisions <WS>/DIRECTOR/BRIEF.md --decisions <WS>/DIRECTOR/DECISION_REGISTER.md
   ```

   舊專案還沒有 `DECISION_REGISTER.md` 才只給 `BRIEF.md` 一個，結果和以前相同。「沒有工單的需求」只有 B 開頭的列算待排項目；DD、PO、OD 的列只是決策紀錄，列出來不代表缺工單。「TRACES_TO 找不到的編號」有東西，是工單對到不存在的編號，改工單。

### 四、選擇頁：要使用者選的放這裡

適用：中途有兩個以上做法、使用者看了才能決定的事，例如 A 風格或 B 風格、版面、配色、角色長相。不適用：純技術選擇（總監自己決定）、要使用者動手的事（照 `docs/03` 待決頁）。

1. **發布**：複製 `templates/choice_page.html`，用 Artifact 工具發布，`capabilities` 給 `{"db": {}, "user": {}, "assets": {}, "comments": {}}`（`comments` 用來叫醒總監，見第六節），`icon` 用 `checklist`。私人頁面，只有使用者看得到；網址寫進 `DIRECTOR_OPERATING_RULES.md`，第一份回報附上。
2. **開題**：用 `ArtifactData` 寫 `decisions/<編號>`：

   ```json
   {"code": "CH-01", "status": "open", "priority": 1, "brief": ["B-2"],
    "title": "主畫面要哪一種風格？", "question": "兩種都照初衷卡 B-2 做，差在感覺。",
    "options": [{"key": "A", "label": "A 明亮", "desc": "白底、大字", "image": {"url": "<圖>", "caption": "A 的主畫面"}},
                {"key": "B", "label": "B 沉穩", "desc": "深色、細線", "image": {"url": "<圖>", "caption": "B 的主畫面"}}],
    "recommended": "A", "why": "B-1 說主要在白天用手機看，亮底比較清楚。"}
   ```

   - 每題都要有 `brief`（對到哪幾條 B）、`recommended` 和 `why`（總監建議和理由，用使用者的話）。對不到初衷卡的題目不要開，先回頭問要不要改卡。
   - 圖：先截真實成品的圖，用 Artifact 工具 `asset: true` 上傳到這一頁，`url` 用上傳結果給的網址。不要用示意圖假裝是成品。
   - 一題只問一件事；選項最多四個。
3. **讀回覆**：每一輪第一個動作，用 `ArtifactData` 查 `decisions` 裡 `status == "answered"` 的，和 `notes` 裡 `status == "new"` 的。同一輪處理：先寫 `seenAt`（第六節），照選擇做或派工，把題目改成 `closed` 並寫 `resolution`、`closedAt`；留言改成 `read`。
4. 聊天裡只說一句「選擇頁新增了 CH-01」，不在聊天裡重複整題。

### 五、不做歪的檢查

1. 每張工單的 `TRACES_TO` 寫它服務的 B 編號（可以和 DD、OD 並列）。
2. 派工前、每個 gate 前跑：

   ```text
   python -I -X utf8 <WS>/DIRECTOR/tools/trace_report.py --orders <WS>/DIRECTOR/orders --reports <報告資料夾> --decisions <WS>/DIRECTOR/BRIEF.md
   ```

   - 「TRACES_TO 找不到的編號」有東西：工單對到不存在的需求，改工單。
   - 「沒有工單的需求」有東西：還有沒做的需求，排進下一批，或問使用者是不是不要了。
3. 成品交件時，對著初衷卡每一列的「怎麼算做到」檢查，結果寫進 gate 報告；最後由使用者看成品說「對」。

### 六、選擇頁不漏讀

選擇頁和待決頁一樣不准漏讀（`docs/03`「PO 的訊息不漏讀」）。

1. **送出就叫醒**：使用者在頁面送出回覆或留言時，頁面用 comments 的 `sendToClaude` 在那一題留一則給總監的訊息。總監的對話開著、而且這一頁的監看是「auto-replies armed」時，總監馬上被叫醒。
   - 發布後、每次恢復（壓縮、換對話）後，用 `ArtifactComments` 列出監看，確認選擇頁是 armed。不是的，請使用者在聊天裡貼一次選擇頁網址，再用 `ArtifactComments` 的 watch 打開。
   - 叫醒只是加速。對話沒開、通知沒送到，第四節第 3 步照樣會在下一輪第一個動作讀到。
2. **已讀回條**：讀到 `answered` 的題目，同一輪先寫 `seenAt`（ISO 時間），再處理、改 `closed`、寫 `resolution` 和 `closedAt`。
   - 頁面上，已回覆卻沒有 `seenAt` 超過 10 分鐘的題目會標出來，使用者看得到總監還沒讀到，可以在聊天裡提醒。
   - 處理晚了照實寫在 `resolution`：幾點才讀到、晚了多久。
3. 處理完，把叫醒用的留言串用 `ArtifactComments` resolve 掉。
4. 每輪結束前自查：選擇頁已讀、沒有「已回覆卻沒關閉」的題目。有總管時，總管例行查的「已回覆超過 10 分鐘還沒關閉」也包含選擇頁。

## 為什麼

- 使用者想做的東西會在對話裡慢慢變形：每一輪的小決定單看都合理，加起來卻偏離一開始想要的。把一開始的需求寫成使用者確認過、只有他能改的卡，每張工單都對回去，偏掉時馬上看得到。
- 風格這類選擇用文字很難描述，使用者看圖才知道要哪個；放在獨立的頁面，使用者有空時點一下就好，也不會在對話裡被其他訊息沖掉。
- 不懂技術的人被問「要不要關這個 plugin」只會卡住。小白模式把這些交給總監的預設，使用者只回答自己真的能回答的事。
