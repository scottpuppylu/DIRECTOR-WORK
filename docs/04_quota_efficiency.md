# 04 額度與效率

## 成本模型

- **每一次模型呼叫，都會把整段上下文再送一次。** 一次工具呼叫 = 一次呼叫。所以成本 ≈ 呼叫次數 × 當時的上下文長度。
- 上下文 = 固定成本（系統工具、工具清單、記憶檔、skill 清單、CLAUDE.md）+ 對話累積（每個工具輸出、每張圖都留著，直到壓縮）。
- 讀入多半是快取讀取。快取有效期：訂閱方案的主對話約 1 小時，subagent 和壓縮約 5 分鐘（官方文件與本機紀錄一致）；壓縮、設定變動、工具清單變動也會讓快取重建。快取讀取對週額度的確切權重沒有公開。
- 跨 session 訊息和定時任務，每次都會讓對方開一輪完整上下文。

### 原專案的實測案例（數字照抄，你的專案請自己量）

- 每次呼叫的上下文中位數 46.5 萬 token；上下文 ≥ 25 萬的呼叫，佔全部讀入的 92%。
- 每次呼叫的固定成本約 4.1 萬：系統工具 1.55 萬、記憶檔 1.23 萬、skill 清單約 9.9k、系統提示（skill 清單有上限，skill 變少 token 不一定變少）。延後載入的工具清單（約 2 萬）不算在內。這是 CLI 的量法；桌面版自帶的工具和指示多，同一資料夾實測多約 4.5 萬，兩者不能直接比。
- 圖片留在上下文裡，之後每次呼叫都重送。
- Bash 輸出佔所有工具結果字元數的 6 成。
- subagent 佔 15% 的呼叫，只佔 5% 的讀入。
- 記憶索引從 8.4k 壓到 2.5k token。

## 用量結構（1.3.0）

- **先問對問題**：檢討用量時，問的是「每單位額度推進了多少交付物」，不是用得快不快、總量多大（教訓 L-034）。不確定 PO 用什麼標準時，先問。
- 每次呼叫依它選的動作歸成五大類：**讀和查**、**協調**、**看圖與審查**、**實際動手**、**等待**。工具：`tools/usage_mix.py`。
- **門檻**（原專案 PO 定的，各專案可改）：讀和查 ≤ 30%，實際動手 ≥ 30%。`usage_mix.py --check` 沒達到就 exit 1。
- 量法：
  - **額度等價量**（每 token）= 輸入 × 1 + 快取寫入 × 1.25 + 快取讀取 × 0.1 + 輸出 × 5。這是相對權重，用來比較，不是官方公布的週額度算法。
  - 一次呼叫的等價量平分給它選的工具呼叫；沒有工具呼叫的算「純文字回覆」。
  - 同一個 `message.id` 會寫成好幾行（usage 在第一行，tool_use 在後面幾行），**先合併再歸類**。只看第一行，大部分費用會被錯歸成純文字回覆。結果出現 80% 這種極端比例，先懷疑解析（L-035）。
  - 分叉或續接的 session 會帶著舊訊息，同一個 `message.id` 只算一次。
- **要減的是沒有產出的重複動作**：重查自己剛做過的、手動輪詢 log、超過輪數的修正。必要的協調、讀上下文、傳訊息是正常的工作成本，不在減量範圍（L-038）。
- 原專案一週實測（約 3 萬次呼叫）：讀和查 44.8%、協調 19.5%、看圖與審查 16.1%、實際動手 14.0%、等待 5.6%，兩個門檻都沒達到。

### 開新 session 划不划算（實測）

提出省額度的措施之前，先用實測算損益兩平：固定成本、重建狀態的成本、每次呼叫的單價曲線（L-036）。原專案同一週的數字（`usage_mix.py` 的 RESTART 行）：

| 項目 | 實測 |
|---|---|
| 新 session 第一次呼叫的上下文（16 個新 session，中位數） | 98.5K |
| 新 session 到第一個實際動手 | 中位數 16 次呼叫、602.8K 等價量（16 個裡只有 1 個在期間內做到，樣本小） |
| 壓縮後到第一個實際動手（75 次壓縮，72 次做到） | 中位數 7.5 次呼叫、201.7K 等價量 |
| 每次呼叫的等價量，依當時上下文 | < 60K：17.4K；60–120K：27.7K；120–170K：26.0K；≥ 170K：26.3K |

- 上下文 ≥ 170K 的一次呼叫（26.3K）不比 60–120K（27.7K）貴，重開省不到單價，只多付重建狀態的約 600K。損益兩平點：**永遠到不了**（`break-even NEVER`）。
- 更早一次、量法不同的檢討也得到同樣結論：新 session 一開始就有 76–81K 的固定上下文；重開後到第一個實際動手，中位數 15 次呼叫、約 370K；上下文 120K 和 170K 以上，每次呼叫 26.0K 對 26.2K。
- 所以**不為了縮上下文開新 session**。這些數字是原專案的；你的專案跑 `usage_mix.py` 看 RESTART 行。只有它印出 `break-even after N more calls`，而且這件工作預計還要超過 N 次呼叫，才考慮重開。

## 規則（依效益排序）

1. **自動壓縮門檻 25 萬（每個專案、每個 worktree）**
   - 在專案的 `.claude/settings.local.json` **同時**寫：
     ```json
     { "autoCompactWindow": 250000, "env": { "CLAUDE_CODE_AUTO_COMPACT_WINDOW": "250000" } }
     ```
   - 單獨跑 CLI 時，只寫 `autoCompactWindow` 就有效；桌面版只有環境變數確定有效（桌面版的原因是推論，沒有隔離證明）。兩個都寫最保險。官方允許 10 萬到 100 萬。
   - `settings.local.json` 通常被 git 排除，所以每個新 worktree 都要重新寫入。用工具：`tools/setup_project_settings.py`，不要手寫。
   - 使用者層設定不動。
   - 驗證：用 `tools/context_probe.py` 看 `autoCompactThreshold`；桌面版看 session 回報的上下文視窗是不是 250000（如果是 100 萬就是沒生效）。
2. **不為了縮上下文換新 session**：長上下文交給規則 1 的壓縮；壓縮前先更新 RESUME_STATE 四行和工單進度，讓摘要可以短。實測重開比留著貴（上面「開新 session 划不划算」）。只在卡死、需要獨立觀點（`docs/01`），或 session 本來就要結束（額度重置、重開機）時換。壓縮或重開後先跑該線的 `status.py`（`tools/status_gen.py` 產生），一次看完狀態，不逐項重查（L-042）。
3. **大量閱讀交給 subagent**：長 log、整份文件、大量搜尋結果，交給 subagent 讀完回傳結論，主 session 不吞原文。subagent 選工具最少、做得完的類型：只讀檔、看圖就用只帶 Read / Glob / Grep 的；general-purpose 帶全部工具，每次呼叫多付幾萬，只在真的要寫檔或跑指令時用（L-040）。
4. **一次做完多步**：互不依賴的工具呼叫放在同一則回覆；多步檢查寫成一支腳本一次跑完。每多一次呼叫，就多付一次整段上下文。
5. **長輸出寫檔，對話只放結論**
   - 預期超過約 50 行的指令輸出、log、JSON、搜尋結果，一律導到檔案，對話只看 `tail`、計數或一行結論。
   - 新腳本預設只印結論，細節加 `--verbose`。
   - 讀長檔用 offset / limit；網頁擷取要帶明確問題，不整頁拿回來。
6. **看圖在短上下文做**：一次要看 3 張以上、或看連續影格時，交給新開的 subagent 或短 session，主 session 只收結論和疑點清單，自己只開少數疑點裁切。
7. **固定成本瘦身**
   - CLAUDE.md 目標 200 行內；細節放在需要時才讀的文件或 skill。
   - 記憶索引 < 3k token（`docs/09`）。
   - 和本專案無關的 plugin：用專案設定 `"enabledPlugins": {"name@marketplace": false}` 只在本專案關掉**使用者自己安裝的** plugin，其他專案不受影響（原專案實測）。
   - 使用者層的 MCP：專案設定 `"deniedMcpServers": [{"serverName": "x"}]` 只在本專案關掉（原專案實測）。
   - 桌面版 / claude.ai 依帳號帶進來的 plugin（`claude plugin list --json` 裡 `scope: synced`）：**專案設定關不掉**（原專案實測），只能在帳號的 plugin 設定關，會影響所有專案；claude.ai connector 的開關也會變成所有新 session 的預設。**這兩類由 PO 決定。**
   - 改完設定，新開一個 session 用 `context_probe.py` 或 Desktop 的上下文數字確認真的變少，不能只看設定檔（L-037）。
   - 不用的 MCP 也一樣：先列清單和估計 token，給 PO 勾。PO 說不關的，之後不要再自動提議。
8. **少叫醒**：定時檢查間隔用 30 分鐘而不是 5 分鐘；等待用背景程序或閒置通知（`docs/03`）。背景工作只等完成通知，或用 Monitor 等條件成立；不手動 `tail` log，只在出問題時看，而且截斷輸出（L-041）。`tools/poll_hint.py` hook 在同一個 session 10 分鐘內讀同一份 log 第 3 次時提示一次，不擋。
9. **routine 工作線用較省的模型**（`docs/05`）。

## 週額度收尾

- **「全速」不等於思考和 token 可以隨便用。** 不因額度快用完就停工，額度到上限就停，重置後接續；但思考程度照 `docs/05`，不發沒有行動價值的訊息、不重複研究、不做無謂的測試。
- 週額度用好用滿：重置時接近用完、而且用在有價值的工作上，剩下沒用也是浪費。預估用不完時，向 PO 建議把排隊中的關鍵工作提前或加開工作線（PO 同意才開）。
- **98%**：開始收尾。能在額度用完前完成的就完成，所有工作存檔。
- **99%**：確定做不完。總監通知所有人強制存檔：本機 commit、更新 RESUME_STATE 四行、停掉自己的排程，等重置後恢復（`docs/06`）。

## 怎麼量（不花額度）

- **固定成本**：`tools/context_probe.py`。原理是把兩行 control request 餵給 `claude --input-format stream-json --output-format stream-json --verbose --no-session-persistence`：
  ```text
  {"type":"control_request","request_id":"i1","request":{"subtype":"initialize"}}
  {"type":"control_request","request_id":"c1","request":{"subtype":"get_context_usage"}}
  ```
  讀 `c1` 的回應（categories、autoCompactThreshold、skills、memoryFiles）。**不呼叫模型。** 兩行之間要等 MCP 連上（工具預設等 20 秒），一啟動就問會漏掉 MCP 那幾列。`totalTokens` 不含 deferred 那幾列。
- **絕對不要用 `claude -p "/context"` 量**：那會真的呼叫模型、花額度。
- **歷史用量**：`tools/usage_report.py` 讀本機對話紀錄的 usage 欄位，只彙總數字，不印內容。紀錄格式不是官方介面，CLI 改版後可能讀不到；官方建議的是 OpenTelemetry 的 token 指標。
- **讀不到數字不等於 0，估計值不能當實測。** 拿不到就寫 `UNKNOWN`，估的就標 `ESTIMATED`。上下文變小也不等於額度省了：改完重量一次，用同樣的工具比前後的數字，才算省到。

## 週期性複查

- 每週一次（或額度重置時）：跑 `usage_report.py` 和 `context_probe.py`，和上週的 `BASELINE_METRICS.md` 比較：每次呼叫上下文中位數、≥25 萬的讀入比例、固定成本、圖片數、Bash 輸出量。
- 同一次加跑 `usage_mix.py --since <上週一> --check`（五大類對門檻、各 session 的比例、RESTART 行）和 `poll_hint.py report --log <動作紀錄> --days 7 --sessions <sessions 檔>`（各線手動讀 log 的次數）。
- 壓縮太頻繁、工作線一直重讀同樣的檔案，就調整門檻（10 萬到 100 萬之間）。
- 新 session 第一次呼叫就很大（原專案中位數 22 萬），代表恢復時帶了太長的摘要：壓縮前先把狀態寫進 RESUME_STATE，讓摘要可以短。

## 防護是安全帶，不是剎車（1.3.1）

- **使用者核准就執行。** PO 在對話裡說可以，就直接做；不要拆設定、請 PO 自己跑，或換個說法再問一次。每多問一輪，就多一次往返和整段上下文，工作線也停在那裡等人。
- **不重複問已核准的事。** 核准仍是一次一件（`docs/08`），但同一件事不問兩次。
- **阻擋只留給明確 opt-in。** `tools/hook_guard.py` 預設只提醒（`--mode remind`），`--mode block` 才擋。擋下已核准的動作，要人來拆設定才推得動，整條線卡住（`docs/10` L-045）。

## 為什麼

- 原專案先以為訊息太多是主因，量了才知道是上下文太長：同一則訊息，上下文 50 萬時的成本是 5 萬時的十倍。
- 壓縮門檻是單一最大槓桿，因為它同時壓低每一次呼叫。
- subagent、長輸出寫檔、短上下文看圖，都是同一件事：不讓原文留在主上下文裡被重送幾百次。
- 開新 session 看起來能縮上下文，但新 session 要重建狀態；實測單價幾乎不隨上下文變大而上升，重開反而比較貴。
- 固定成本每次呼叫都付，幾千 token 乘上幾千次呼叫就很可觀；但會影響其他專案的開關，不是總監能決定的。
- 量測要不花額度，否則量測本身就變成成本。
