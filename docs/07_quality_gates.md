# 07 品質閘門

## 規則

### 1. 工程狀態和成品狀態分開回報

- 工程：編譯、測試、雜湊、效能數字。成品：使用者實際看到、聽到、用到的東西。
- **數字不能代替看成品。** 單元測試、量測 JSON、build 成功、工具跑完，都不是成品通過。
- 寫了程式、worker 說完成、commit 成功、單一測試通過、文件更新，都不等於完成。必要驗收全部達成且有證據才是 PASS，沒驗證的寫 UNVERIFIED。
- 開發中就要看真實輸出：每個重要修改之後就看，不是只在最後看。

### 2. 三層盲審包

正式候選的成品審查，由 worker 準備三層，放在同一個審查包資料夾：

| 層 | 內容 | 不能有 |
|---|---|---|
| `BLIND/` | 成品本身（圖、錄影抽格、輸出樣本），固定檔名，附一份只描述「要審什麼」的問題 | 分數、PASS 字樣、作者結論、修了什麼、預期答案 |
| `TECHNICAL/` | 量測、log、測試結果、修改清單 | — |
| `ANSWER_KEY/` | 作者認為的已知缺陷、修正對照、預期結果 | — |

- 審查順序：盲審 reviewer 只看 `BLIND/` → 總監自己看關鍵成品 → 看 `TECHNICAL/` → 最後開 `ANSWER_KEY/` 對照。
- 盲審 reviewer 是總監開的 subagent，工具只給 Read / Glob / Grep，只指向 `BLIND/`。
- 每個審查包附 manifest（檔名、大小、SHA-256、來源 commit、分類）；單檔大小設上限（原專案 50 MB）。
- 不准為了好看而準備審查包：不挑隱藏缺陷的視角、不修圖、不在盲審層放任何暗示。
- **盲審稽核**：審完後檢查 subagent 的對話紀錄，每一個工具呼叫都必須是 Read / Glob / Grep，且路徑都在 `BLIND/` 內；不合格的審查作廢（`REVIEW_INVALID`）。審查因額度或錯誤中斷，也寫 `REVIEW_INVALID`，不寫通過。
- 盲審一次只跑一個；只用在正式候選，中間迭代由總監看關鍵總覽。
- 總監自己的審查標 `DIRECTOR_REVIEW`，不是第三方獨立審查。

### 3. 成品常識閘門（先於任何細部審查）

有成品的工單，常識閘門寫成 `REVIEW` 類型的驗收條件，開工前就寫明誰看、從哪個角度看、看多大範圍（`docs/02`）。看的角度不由實作者挑。

先用白話描述成品，當自己是第一次接觸這個產品的使用者：誰（或什麼）在做什麼、往哪裡、結果是什麼。然後逐題答 `OK / WRONG / 看不到`。「看不到」不算通過，要補證據。

| # | 問題 |
|---|---|
| 1 | 方向與目的：每個元素都朝向它該朝的目標、做它該做的事嗎？ |
| 2 | 因果：動作和結果銜接嗎？有沒有東西憑空出現、跳動、沒有原因就改變？ |
| 3 | 每個元素：不只主角，背景和次要元素都合理嗎？有沒有僵住、重複、消失的？ |
| 4 | 形狀與比例：整體輪廓和比例像真的嗎？ |
| 5 | 對稱：一側有問題，另一側一定要看；成對的東西兩邊都要答。 |
| 6 | 破損：破圖、空洞、穿插、閃爍、亂碼、截斷？ |
| 7 | 完整性：該有的元素都在嗎？數量對嗎（逐項點數）？ |
| 8 | 規格：尺寸、距離、單位、規則和真實世界或規格書一致嗎？ |
| 9 | 流程：從啟動到第一個可用畫面或結果，有沒有空白、閃爍、順序錯、跳接？ |
| 10 | 第一印象：不看任何說明，一般使用者 3 秒內會不會覺得哪裡怪？說出第一個覺得怪的地方。 |

- 證據規格不由作者挑：固定的視角或測試情境、全尺寸（全解析度）的局部、關鍵時刻前後的連續樣本、從啟動開始的完整流程抽樣。縮圖或總覽不算通過。
- Worker 交件前先填這張表，附在 TASK REPORT；沒附就退回。
- **給 PO 之前，總監的責任**：
  1. 大量查看交給短上下文（新的 subagent 或短 session）逐項填表，每格附檔案路徑和位置；總監主 session 只開標 WRONG 或「不確定」的幾個（約 6 個以內），全部沒疑點時至少抽看 1 個。代看的人不是盲審。
  2. 盲審另外跑一次，和總監的表格對照，兩邊都沒有 WRONG 才給 PO。
  3. 有已知缺點仍要給，第一行就寫出來。
  4. PO 指定的急件也不能跳過第 1 點；第 2 點可以因時間省略，但要寫明沒有盲審。
- **漏檢紀錄**：每次 PO 先發現問題，就加一行（日期、PO 發現什麼、為什麼漏、補了哪條檢查），並把那條檢查加進閘門。

### 4. 修正

- **在隔離的候選版本裡修，不直接改主線**；每次修正先寫根因假設。
- **3 輪為一組**（1 個主修正 + 2 次有根因的定向修正）。同一根因兩輪沒進展就停，比對證據，判斷是不是環境、架構、測試或治理本身的問題。
- 一組沒過，第 4 輪（之後每組結束）必須是**深度根因研究**，寫進 `ROOT_CAUSE_STUDY.md`：問題實際出在哪裡（`WHERE:`）、有沒有更好的解法，例如現成素材、其他方法或改設計（`ALTERNATIVES:`）、決定（`DECISION:`）。研究完才開下一組 3 輪，可以循環。換人不重置次數（L-032）。
- 組別、輪次和研究檔路徑寫進 RESUME_STATE 的 `FIX_ROUNDS:`；`tools/round_check.py` 檢查，沒有研究就開第 4 輪的 FAIL，總監駁回。專案的 guard_check 對每個 worktree 跑它。
- 比對腳本要分出 `FIELD_MISSING`、`MISMATCH`、`N/A`：欄位缺失不能當成值不同，也不能靜默通過，報告寫明是工具問題。新增檢查段時，先確認它會輸出哪些欄位（L-022）。
- 每次修正後，用**同樣的情境、同樣的視角**重做一次，保留前後對照和差異（例如像素 diff），證據不刪。
- 不准為了 PASS 跳過 gate、偽造證據、刪測試、降低安全要求。

### 5. 不破壞已通過的東西

- 修一個地方後，檢查其他已通過的部分和凍結的基準。
- 核心邏輯的結果（例如固定輸入的輸出雜湊）必須維持一致，除非工單明確允許改。
- 新行為一律用新的版本 ID，不改凍結的歷史版本。

### 6. 最終驗收屬於 PO

- 總監和 worker **絕不自稱最終通過**（例如 ART_PASS、OWNER_PASS、RELEASE_READY）。總監最高只寫「建議 PO 驗收」。
- 審查系統本身沒驗證、審查失敗、或沒跑，都要照實寫，不可以說檢查通過。
- PO 的回覆要綁到 PO 看的那個成品：候選 ID、commit、入口檔、manifest SHA-256 和訊息編號，寫成 `PO_PRODUCT_REVIEW` 或 `PO_ACCEPTANCE.json`（`docs/02`）。綁不到的回覆不能拿來說「PO 看過這一版」。初衷卡改過之後，舊版的「看過」不算看過新條件。
- 「綁到成品」是指成品檔現在還在、內容和紀錄的雜湊相同（2.2）。只寫了雜湊、沒有檔可以核對的回覆是「成品待核對」，不是已驗收。
- worker 自己寫的 PASS 和證據紀錄只是自述（2.2）。說「這版驗證過」要四樣都有：worker 自述、合格的證據紀錄、鎖定的初衷卡、總監自己重跑通過（DIRECTOR_LOG 的 `EVIDENCE_RERUN` 行）。重跑時加 `--brief` 發現初衷卡條件變了（行尾 `brief=stale` 或 `brief=unconfirmed`），這次重跑不算。
- `PO_PRODUCT_REVIEW` 只認整行紀錄，這是刻意的設計（2.2 說明），和 `DISPATCH`、`EVIDENCE_EQUIVALENT`、`EVIDENCE_RERUN` 一樣：一行從頭就是這個紀錄（前面可以有「日期 |」，後面可以有「| 備註」）。用 `>` 引用的、縮排的、在 ``` 區塊裡的、夾在別的句子中間的，都只是資料，不算 PO 回覆。理由：LOG 裡常會貼 worker 報告、聊天內容或範例；如果引用的字也算，貼一段文字就能假造「PO 看過」。總監記 PO 回覆時，自己另起一行寫完整的紀錄。

### 7. 新增閘門與來源資料

- 新增閘門時，同時列出所有既有素材，逐一補跑；沒過或還沒跑的標「未驗」，不能當成已過。
- 來源的中繼資料（影格率、單位、類型）在匯入時實測並記錄，不沿用假設。

## 範例：視覺類專案（選用）

- 固定機位：例如主體背後、正面、左側、右側四個固定攝影機，每個機位看完整動作，連續影格涵蓋開始到結束。
- 全解析度局部：畫面裡每一個人物的頭肩、雙手、雙腳，不只主角；人太小就再拍一個近的版本。
- 關鍵時刻（接觸、放開、落地）前後各至少 5 個連續影格。
- 從載入到第一個可用畫面，每 0.5 秒抽一張。
- 自動探針只用來提早抓錯：朝向角度、物體間距、長時間不動的角色、重複或跳動的位置、載入到第一個畫面的時間。探針數字正常不代表畫面正常。
- 看圖有上限：大量讀圖可能撞到一段時間內的讀圖額度（原專案約 2 小時 70 張），盲審一次只跑一個、每張只開一次、總覽優先。

## 為什麼

- 原專案最嚴重的漏檢，都是「數字對了，就沒人再看成品」：路徑正確，但主體的方向是反的；被問到的一側修好了，另一側沒人看；背景的角色一直僵著。
- 審查者看到作者的結論，就會被結論帶走；所以先看成品、後看答案。
- 作者挑的視角，常常剛好避開缺陷；固定視角讓缺陷沒地方躲。
- 修正沒有上限，就會一直修、一直花；三輪後換方法或回報，比第十輪更有價值。
- 最終驗收是 PO 對產品的判斷，不是流程能代替的。

## 發布前看 CI（1.3.2，L-046）

- 合併、打 tag、建 Release 之前先看遠端 CI（`gh pr checks <PR>`）：全綠才發布。本機三版 selftest 通過不能取代 CI：runner 的 Python 小版本和本機不同。
- tag 打錯不移動、不刪；修好後發下一個 PATCH。
