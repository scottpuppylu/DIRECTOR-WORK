# 06 無損續航

目標：額度用完、錯誤、當機、重開機、PO 手動停止之後，每條工作線都從最後一個已驗證的 checkpoint 接著做，不重做已完成的事，也不沿用半成品。

## 規則

### RESUME_STATE.md

- 每條工作線在自己的工作資料夾根目錄維護一份（`templates/RESUME_STATE.md`），路徑登記在 `ACTIVE_WORKSTREAMS.md`。
- **頂部固定四行**，只看這四行就要能接手：
  ```text
  PROGRESS: 做到哪裡（最後完成的一步、commit、證據路徑）
  DOING: 正在做什麼（屬於哪張工單的哪一項）
  NEXT_STEP: 接下來的精確動作，可以直接照做
  COMMS: 我在等誰（等什麼）／誰在等我（欠誰什麼）／做完要通知誰；沒有就寫 NONE
  ```
- 下面再寫：工單路徑、session、worktree / branch / HEAD、最後驗證的 checkpoint、完成步驟（附證據）、`IN_FLIGHT`（背景程序 PID、啟動時間、輸出路徑、完成判定方式；也列出自己設的計時器和等待程序）、要丟棄的半成品、等待中的決定、`DO_NOT_REPEAT`（失敗過的方法）。
- **何時更新**：每個 checkpoint commit 之後、送 TEST REQUEST 之前、背景程序啟動和結束時、收到總監決定時、壓縮之前。寫完才做下一步。
- `UPDATED` 時間一律讀系統時鐘（`date`），不估計。
- 寫完用 `tools/gate_check.py --resume <檔案>` 檢查四行有沒有寫齊。它只看格式，內容對不對還是要靠 `LAST_VERIFIED_CHECKPOINT` 和 repo 核對。
- 平常就要做，不是快停才做：有成果就 commit。進度不能只留在對話裡。

### 恢復程序（任何 session 被打斷後第一件事）

1. 重讀：工單 → 自己的 RESUME_STATE → 專案 CLAUDE.md → 本專案版規則（總監另讀 `DIRECTOR_STATE.md`）。
2. `git status`、`git log -3`，和 RESUME_STATE 的 HEAD 比對；不一致先查原因，不覆寫。
3. IN_FLIGHT：只檢查自己的 PID。程序不在了，就看完成判定檔；不完整就列入重做。**中斷的擷取、量測、打包、匯入一律重做，不沿用。**
4. 被中斷的 GO：通知總管「RESUMED <task>，需要重新排程」，不假設時段還有效。
5. 自己設的計時器、背景等待、監看程序：全部視為可能失效，逐項確認或重建。
6. 更新 RESUME_STATE（時間 + 恢復說明），先處理 COMMS 裡欠別人的，才繼續 NEXT_STEP。
7. 第一則給總監的訊息只有一行：`RESUMED <TASK_ID> at <checkpoint>; next=<step>; waiting=<誰或 NONE>`。沒有需要總監知道的事就不發。

PO 手動停止後再讓它繼續，也要先完整跑一次這個程序：停止那一刻的指令可能只跑了一半，背景程序可能變成沒人管的孤兒程序。

### 總監自身的恢復

1. 讀待決頁上 PO 已回覆的項目和新留言（`docs/03`）。
2. 讀 `DIRECTOR_LOG.md` 最後 30 行，找出還沒處理完的 PO 指示。
3. 讀 `ACTIVE_WORKSTREAMS.md`、未讀的 worker 訊息；有 session 清單工具就對照各 session 的狀態。
4. 跑機制檢查（下一節），缺的重建。
5. 補發被中斷的工單或決定。

### 機制要能重建（guard check）

- 每個排程和防護機制（壓縮設定、喚醒計時器、排程任務、閒置監看、快照）都不能只活在 session 記憶裡。每一項要有：**檔案紀錄、檢查方法、重建指令**，寫在 `DIRECTOR/GUARDS.md`。
- 寫一支只讀的檢查腳本（原專案叫 `guard_check`），逐項印 `OK / MISSING` 和重建指令，缺任何一項 exit 1。總監每次喚醒、壓縮或恢復後先跑它；重建由總監在自己的 session 背景執行（背景程序要屬於總監，才能叫醒總監）。
- 新增任何機制時，同一步就要加進 GUARDS 表和檢查腳本，否則不算完成。

### 額度重置後的喚醒

- 主要機制：總監 session 的背景計時器，睡到「下一次重置 + 3 分鐘」。醒來時：確認重置生效 → 找出被額度打斷、之後沒有完成回報的 session → 送 `RESUME` → **立刻設下一個計時器** → 在 DIRECTOR_LOG 記一行。
- 備援：環境若有 app 層的排程任務，設一個在週重置後執行的恢復任務，和計時器互為備援。排程任務需要電腦開著、app 開著、連網；需要的權限模式由 PO 設定，先演練一次確認不會卡在權限詢問。
- 背景程序在重開機或關 app 後會消失，所以不能假設計時器一定會響；恢復鏈要有一條不依賴 session 記憶的路。
- 各 worker 收到 RESUME 後自己讀檔接續；總監不替別人讀它的檔案。
- 有限額度時唯一的取捨是**順序**：重置後先恢復 P0 和 gate 收尾的工作線。

## 為什麼

- 任何 session 隨時可能被打斷。只要進度寫在檔案裡，打斷就只是暫停；只寫在對話裡，打斷就是損失。
- 四行頂部是因為恢復時最需要的就是這四件事，而且它們要能在幾秒內讀完。
- 半成品看起來完整，其實可能只跑了一半；重做比追查便宜。
- 原專案有一次 worker 在清單還沒做完時就結束回合，閒置了 80 分鐘沒人發現。之後才加了閒置監看，並規定「真的要等，就寫明在等誰、等什麼，並用背景等待觸發」。
- 機制要能重建，因為重開機、壓縮和額度重置都會讓背景程序消失，而 session 自己不會記得它曾經設過什麼。
