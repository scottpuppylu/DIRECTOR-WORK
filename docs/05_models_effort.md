# 05 模型與思考程度（effort）

## 可用的模型（名稱會更新，以官方為準）

| 名稱 | 模型 ID |
|---|---|
| Opus 5.5 | `claude-opus-5-5` |
| Sonnet 5.5 | `claude-sonnet-5-5` |
| Haiku 5.5 | `claude-haiku-5-5` |
| Fable 5.1 | `claude-fable-5-1` |

effort 等級：`low / medium / high / xhigh / max`。

本文件不對個別模型的能力做宣稱；下面的分配是原專案的做法，用之前先看官方說明，再用自己專案的結果調整。

## 規則

### 判斷原則：重要程度 × 難度

- **重要且困難 → xhigh**；**重要或困難其一 → high**；**其餘 → medium**。
- worker 最低 medium。只有「只收發指令、不需要判斷」的線（例如清理員只照清單做）才用 low。
- **max 只臨時用**：同一難題兩輪有根因的修正都失敗、要做最後一次深度根因分析時才開；寫進 `DIRECTOR_LOG.md`，解決後調回。
- 只在工作線換到重要度或難度明顯不同的階段時才調整，不每次開工都重評。
- 環境若提供設定 session effort 的工具（例如 `set_session_effort`），總監用它調整 worker；通常下一輪生效，不必停 session。總監自己的 effort 由 PO 設定。

### 依角色

| 角色 | 建議模型 | 建議 effort | 說明 |
|---|---|---|---|
| 總監 | 最強可用模型 | high | 以分派、裁決為主；大量閱讀和看圖交給 subagent |
| 總管（排程） | Sonnet 級 | medium | routine 排程；規則判斷交總監 |
| 清理員 | Sonnet 級 | low–medium | 照清單盤點與比對；刪除前的保護檢查要寫清楚 |
| Worker：關鍵路徑、架構決策、困難除錯 | 最強可用模型 | xhigh | 例如核心演算法、資料格式、品質最落後的領域 |
| Worker：重要但做法已知 | 最強可用模型 | high | |
| Worker：一般實作、截圖、參數實驗 | 最強可用模型或 Sonnet 級 | medium | 卡在根因時個別調高 |
| 盲審 reviewer（subagent） | 最強可用模型 | 預設 | 品質判斷不省；工具只給 Read / Glob / Grep |
| 機械性 subagent（搜尋、彙整 log、格式轉換） | Haiku 或 Sonnet 級 | 預設 | 只回傳結論 |

### 選用角色（2.1.0 從 `docs/01` 移來）

| 角色 | 是誰 | 做什麼 | 不做什麼 |
|---|---|---|---|
| 總管（排程） | 一個 session | 排程共用重資源（GPU、長 build、量測時段），寫排程看板 | 不決定優先序（照總監給的）；不改程式 |
| 清理員 | 一個 session | 磁碟盤點、備份、經擁有者同意後刪除 | 不刪有依賴或受保護的資料 |
| 盲審 reviewer | 總監開的 subagent，只有 Read / Glob / Grep | 只看審查包的盲審層，列出缺陷與證據（`docs/07`） | 不看答案、不看分數、不寫檔 |

專案沒有共用重資源，就不要總管；磁碟不吃緊，就不要清理員。

### 派工規劃（2.1.0）

總監的職責範圍不變（`docs/01`）。要改的是做法：每次派工前先想清楚怎麼分給工人，不把實作都攬進總監自己的 session。

- **規劃要回答**：要不要開 worker、開幾個；依檔案歸屬怎麼切（同一個檔案只給一個人，Single Writer）；平行還是先後（後一個要用前一個的結果，就排先後）；每個 worker 的模型和 effort（照本檔「判斷原則」）；誰整合、誰驗收（不是寫的人自己）。
- **寫在哪裡**：寫進工單，或 `DIRECTOR_LOG.md` 的 DISPATCH 那一筆；恢復時看得到當初怎麼分。
- **總監自己做的**：讀、規劃、寫工單、審證據、裁決、管續航（`docs/01` 的職責）。改檔、跑測試這類實作交給 worker，驗收才是中立的。
- 一件事只有一個人做最快、拆開反而要多整合時，就只開一個 worker，並在規劃裡寫一句為什麼。

### 不要為省額度犧牲品質的界線

下面這些**不降**模型或 effort：P0 阻擋的根因分析、gate 裁決、正式候選的盲審、安全與資料完整性相關的修改、要給 PO 看的成品檢查。
要省，先從上下文長度省（`docs/04`），不是從思考省。

## 防護是安全帶，不是剎車（1.3.1）

- **使用者核准就執行。** 不論用哪個模型、多高的 effort，都不要因為「保險起見」把已核准的動作退回給 PO。
- **不重複問已核准的事。** 只有不確定是不是同一件事時，才問一句。
- **阻擋只留給明確 opt-in**（`tools/hook_guard.py --mode block`）。預設的提醒模式下，hook 的提醒是給模型的上下文，不是禁止：使用者已核准就照做（`docs/10` L-045）。讀機密（G50–G52）和暫停旗標例外，每個模式都擋。

## 為什麼

- 一律最高很浪費；一律最低會做錯、返工，返工更貴。用「重要 × 難度」分配，簡單又可解釋。
- 原專案試過 low：判斷錯誤多，PO 要求 worker 最低 medium。
- routine 線（排程、清理）大部分時間在讀檔、比對、寫一行，用較省的模型就夠，而且這兩條線被叫醒的次數最多。
- 盲審和裁決是品質的最後一道防線，省在這裡會讓整條線的努力白費。
- 總監自己做實作，上下文變長、平行變排隊，也沒有中立的驗收（`docs/10` L-057）。
- 原專案量到幾乎所有呼叫都跑最強模型，改用較省模型的規則要事後量測確認真的生效（`tools/usage_report.py` 的模型分佈）。
